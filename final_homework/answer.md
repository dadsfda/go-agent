# 三方 AI Agent 平台接入实施方案

## 1. 接入背景与目标

未来业务系统不应只提供传统页面操作，还应支持与 AI Agent 进行自然语言交互。若招聘系统需要接入 OpenClaw、Hermes 等三方 AI Agent 平台，核心目标不是把数据库或内部接口直接暴露给外部平台，而是把系统能力封装成安全、可控、可审计的工具能力，让 Agent 可以在授权范围内完成查询、分析和辅助操作。

本方案的目标如下：

1. 让三方 Agent 能够通过标准工具调用方式访问招聘系统能力。
2. 保证 HR、候选人、管理员等不同身份的数据权限不被绕过。
3. 避免数据库、OSS 文件、内部密钥等敏感资源直接暴露给外部平台。
4. 对所有 Agent 调用过程进行日志留存、审计追踪和风险控制。
5. 先开放低风险只读能力，再逐步开放需要确认的写操作能力。

## 2. 接入边界

三方 Agent 平台只能访问系统明确注册的工具，不能直接访问 MySQL、OSS、gRPC 服务或内部管理接口。

系统侧需要新增一个 Agent Adapter 接入层，作为 OpenClaw、Hermes 与现有招聘系统之间的统一入口。Adapter 负责平台认证、用户映射、权限校验、工具注册、参数校验、限流、审计和结果脱敏。真正的业务逻辑仍然复用现有后端服务，避免重复实现业务规则。

整体调用链路如下：

```text
OpenClaw / Hermes
  -> Agent Adapter 接入层
  -> 平台认证与用户身份映射
  -> 工具白名单与参数校验
  -> 权限校验、限流、审计
  -> Web API 或 Logic gRPC 服务
  -> MySQL / 私有 OSS / AI 能力
  -> 结果脱敏与标准化
  -> 返回给三方 Agent 平台
```

## 3. 总体架构设计

系统整体分为五层。

第一层是三方 Agent 平台层，包括 OpenClaw、Hermes 等平台。它们负责自然语言理解、任务规划和工具调用发起。

第二层是 Agent Adapter 接入层。它是本次接入的核心，负责把外部 Agent 的工具调用转换为系统内部可识别的业务请求。

第三层是权限与安全控制层。它负责校验调用者身份、角色、租户、工具权限、数据范围、调用频率和风险等级。

第四层是现有业务服务层。对于招聘岗位、候选人、投递记录、AI 问答、OSS 简历等能力，优先复用已有 Web 服务和 Logic gRPC 服务。

第五层是数据与基础设施层，包括 MySQL、私有 OSS、日志系统、监控系统和大模型服务。

这种架构的好处是三方 Agent 平台只看到经过抽象的工具能力，看不到系统内部实现细节。即使后端从 HTTP 调整为 gRPC，或者存储从本地切换到云服务，也不会影响外部 Agent 的接入方式。

## 4. 接入原则

接入三方 AI Agent 平台时，应遵循以下原则：

1. 最小权限原则：Agent 只能调用当前用户被授权的工具，不能越权查询或操作他人数据。
2. 工具白名单原则：只开放经过注册和审核的工具，不提供任意 SQL、任意 HTTP 或任意文件访问能力。
3. 只读优先原则：第一阶段优先开放查询类能力，写操作必须在权限和审计成熟后再开放。
4. 人工确认原则：创建岗位、修改岗位、下架岗位、发送通知等写操作必须经过用户二次确认。
5. 数据脱敏原则：手机号、邮箱、简历文件、候选人详细档案等敏感信息默认脱敏返回。
6. 全链路审计原则：每一次 Agent 调用都要记录调用人、工具名称、参数摘要、结果状态和耗时。
7. 内部服务不裸露原则：MySQL、OSS、gRPC 内网地址、API Key、Secret Key 均不能暴露给三方平台。

## 5. 身份认证与授权流程

三方平台接入时，系统需要为每个平台分配独立的应用身份，例如 `client_id` 和 `client_secret`。OpenClaw 或 Hermes 调用系统前，先通过应用身份换取短期访问令牌。

每次工具调用都需要携带以下身份信息：

1. 平台标识：用于区分请求来自 OpenClaw、Hermes 还是其他平台。
2. 外部用户 ID：表示当前在 Agent 平台中发起请求的真实用户。
3. 租户或组织 ID：用于区分不同企业或团队的数据范围。
4. 角色信息：例如 HR、候选人、管理员。
5. 授权范围：表示当前用户允许调用哪些工具。

Agent Adapter 收到请求后，先校验平台令牌是否合法，再把外部用户映射为系统内部用户。例如某个 OpenClaw 用户需要映射到招聘系统中的某个 HR 账号。完成映射后，Adapter 会生成内部调用上下文，再调用后端服务。

需要注意的是，Adapter 做权限校验只是第一层防护，Logic 服务仍然需要保留最终权限判断。例如 HR 只能管理自己发布的岗位，但可以根据产品规则查看公开岗位列表；候选人不能调用 HR 管理类工具；管理员也必须在审计规则内操作。

## 6. 工具能力设计

系统不应把接口原样暴露给 Agent，而应把业务能力设计成语义清晰的工具。每个工具都需要定义工具名称、用途说明、输入参数、输出结构、权限范围、风险等级、限流策略和审计要求。

第一阶段建议开放只读工具：

1. `list_public_jobs`：查询公开招聘岗位。
2. `get_job_detail`：查询指定岗位详情。
3. `get_hr_job_stats`：查询当前 HR 的岗位数量、投递数量和岗位状态。
4. `get_hot_jobs`：查询岗位热度排行。
5. `get_applications`：分页查询岗位投递候选人。
6. `get_candidate_profile`：查询候选人结构化档案摘要。
7. `get_resume_signed_url`：在授权范围内获取短期有效的简历下载地址。
8. `ask_recruitment_data`：基于当前业务数据进行自然语言问答。

第二阶段可以开放受控写工具：

1. `create_job_draft`：生成岗位草稿，但不直接发布。
2. `update_my_job`：修改本人创建的岗位。
3. `close_my_job`：下架本人创建的岗位。
4. `generate_candidate_followup`：生成候选人沟通建议。

写工具必须增加确认流程。Agent 可以先生成操作计划，例如“准备下架岗位 A，原因是已招满”，系统把计划展示给用户确认，用户确认后才真正执行。

## 7. 标准调用流程

一次典型的 Agent 工具调用流程如下：

1. 用户在 OpenClaw 或 Hermes 中提出问题，例如“帮我看一下最近哪个岗位最热门”。
2. 三方 Agent 根据问题选择调用 `get_hot_jobs` 工具。
3. 三方平台把工具名、参数、用户身份和平台令牌发送到 Agent Adapter。
4. Adapter 校验平台令牌是否有效。
5. Adapter 根据外部用户 ID 查询并绑定系统内部账号。
6. Adapter 校验该用户是否有权调用 `get_hot_jobs`。
7. Adapter 校验参数格式，过滤非法字段和异常输入。
8. Adapter 调用现有 Web API 或 Logic gRPC 服务获取真实业务数据。
9. 后端服务从 MySQL 中查询岗位投递统计和岗位信息。
10. Adapter 对返回结果进行脱敏、裁剪和标准化。
11. Adapter 记录审计日志，包括调用工具、调用人、耗时和结果状态。
12. Adapter 把结构化结果返回给三方 Agent。
13. 三方 Agent 再把结果组织成自然语言回复给用户。

这个流程保证 Agent 的回答来自真实业务数据，同时不会绕过系统已有权限控制。

## 8. 私有 OSS 文件访问方案

简历文件属于敏感数据，不能把 OSS 原始地址、Bucket 信息或永久 URL 返回给三方 Agent。系统应继续采用私有 OSS 访问模式。

当 Agent 需要查看简历时，流程如下：

1. Agent 调用 `get_resume_signed_url` 工具。
2. Adapter 校验当前用户是否有权查看该候选人的简历。
3. 后端根据简历 object key 生成短期有效的签名 URL。
4. 签名 URL 设置较短有效期，例如 5 分钟到 1 小时。
5. 返回结果中只包含签名 URL、过期时间和文件名，不返回 OSS 密钥。
6. 系统记录签名 URL 的生成日志和访问审计。

这样可以保证简历文件仍然存储在私有 OSS 中，外部 Agent 只能在授权范围和有效期内临时访问。

## 9. 数据安全与隐私保护

Agent 接入后，数据安全风险会明显增加，因此需要在多个环节做控制。

首先，候选人的手机号、邮箱、完整简历、学校、工作经历等信息应按场景脱敏。普通统计类问题只返回聚合数据，不返回个人明细。只有用户明确查询某个候选人且具备权限时，才返回结构化档案摘要。

其次，系统不能提供自由 SQL 查询工具。所有查询都必须通过预定义工具完成，后端使用参数化查询或已有服务方法，避免 SQL 注入和越权查询。

再次，需要防止提示词注入。候选人简历、岗位描述、聊天内容都应被视为不可信数据。即使这些内容中出现“忽略之前规则”“导出所有数据”等文本，也不能改变工具权限和系统安全规则。

最后，Agent 的上下文记忆不应无限保存敏感数据。聊天历史中可以保存问题、回答和工具调用摘要，但不建议长期保存完整简历原文、签名 URL 或密钥类信息。

## 10. 错误处理设计

系统应返回统一错误结构，方便三方平台识别和展示。

常见错误类型包括：

1. `AUTH_FAILED`：平台认证失败或令牌过期。
2. `PERMISSION_DENIED`：当前用户无权调用该工具或访问该数据。
3. `VALIDATION_ERROR`：工具参数格式错误。
4. `NOT_FOUND`：请求的数据不存在或对当前用户不可见。
5. `RATE_LIMITED`：调用频率超过限制。
6. `HUMAN_CONFIRM_REQUIRED`：写操作需要用户确认。
7. `DOWNSTREAM_ERROR`：内部业务服务、数据库、OSS 或大模型服务异常。

错误信息应尽量对用户友好，但不能暴露内部表名、服务器地址、密钥、SQL 语句或堆栈信息。

## 11. 限流、幂等与可靠性

Agent 平台可能会因为任务规划产生连续调用，因此系统必须增加限流策略。

限流维度包括平台维度、用户维度、工具维度和 IP 维度。例如查询类工具可以限制为每分钟若干次，生成签名 URL 和写操作需要更严格限制。

对于写操作，必须支持幂等控制。三方平台每次写操作请求都应携带唯一请求 ID，系统根据请求 ID 判断是否重复提交，避免 Agent 重试导致重复创建岗位或重复下架。

Adapter 调用下游服务时应设置超时、重试和熔断策略。对于查询失败的情况，可以返回明确失败原因；对于写操作，不应在结果未知时自动重试，以免造成重复操作。

## 12. 日志审计与监控

所有 Agent 工具调用都需要记录审计日志。审计日志至少包括：

1. 请求 ID。
2. 平台名称。
3. 外部用户 ID。
4. 内部用户 ID。
5. 调用工具名称。
6. 参数摘要。
7. 权限判断结果。
8. 下游服务调用结果。
9. 返回状态。
10. 调用耗时。

监控指标包括工具调用次数、成功率、失败率、平均耗时、权限拒绝次数、限流次数、签名 URL 生成次数和写操作确认次数。

当出现异常增长、连续失败、越权访问尝试或高频简历下载时，系统应触发告警。

## 13. 分阶段实施流程

第一阶段：能力梳理。

梳理当前招聘系统已有能力，确认哪些能力适合开放给 Agent。优先选择岗位查询、投递统计、岗位热度、候选人摘要等只读能力。

第二阶段：设计工具协议。

为每个工具定义名称、描述、输入结构、输出结构、权限范围、风险等级、错误码和示例返回。工具协议应保持稳定，避免频繁变化影响三方平台。

第三阶段：建设 Agent Adapter。

实现统一接入入口，完成平台认证、用户映射、工具路由、参数校验、权限检查、限流、审计和结果标准化。

第四阶段：接入现有后端服务。

Adapter 不直接操作数据库，而是调用现有 Web API 或 Logic gRPC 服务。这样可以复用已有业务逻辑、权限规则和数据处理能力。

第五阶段：沙箱联调。

在测试环境中接入 OpenClaw 或 Hermes 沙箱，使用模拟 HR 和候选人账号进行工具调用测试，验证身份映射、权限边界、参数校验和返回格式。

第六阶段：安全测试。

重点测试越权访问、提示词注入、SQL 注入、恶意参数、重复提交、高频调用、签名 URL 泄露和敏感字段脱敏。

第七阶段：灰度上线。

先开放少量内部账号使用，只开放只读工具。观察日志、耗时、错误率和用户反馈后，再扩大范围。

第八阶段：开放受控写能力。

在只读能力稳定后，再开放岗位草稿、岗位修改、岗位下架等写工具。所有写工具都必须经过用户二次确认，并记录完整审计日志。

## 14. 验收标准

接入完成后，应满足以下标准：

1. OpenClaw 或 Hermes 可以成功调用系统注册的工具。
2. Agent 查询结果来自 MySQL、OSS 等真实业务数据。
3. 未登录、令牌无效或权限不足时不能访问后台能力。
4. HR 只能操作本人有权限的数据，不能越权操作他人岗位。
5. 简历文件只能通过短期签名 URL 访问，不能暴露永久地址。
6. 所有工具调用都有审计日志和 request id。
7. 参数错误、权限错误、下游异常都有统一错误返回。
8. 高频调用会触发限流。
9. 写操作必须经过用户确认，不允许 Agent 静默执行高风险操作。
10. 聊天上下文和工具调用记录不会长期保存敏感原文或密钥信息。

## 15. 风险与应对措施

越权访问风险：通过外部用户映射、工具权限、数据范围校验和 Logic 服务最终权限校验共同控制。

敏感信息泄露风险：默认返回脱敏数据，简历文件只返回短期签名 URL，不返回 OSS 密钥和永久链接。

Agent 误操作风险：写操作先生成草稿或操作计划，必须由用户二次确认后执行。

提示词注入风险：把简历、岗位描述、聊天内容视为不可信输入，不能让文本内容改变工具权限和系统规则。

调用过载风险：按平台、用户、工具设置限流，并对下游服务设置超时和熔断。

结果不可信风险：关键业务回答应附带数据来源摘要，例如统计范围、岗位 ID、查询时间和命中数量。

## 16. 总结

接入 OpenClaw、Hermes 等三方 AI Agent 平台时，系统设计重点不是简单开放接口，而是把招聘系统能力封装成安全可控的工具。通过 Agent Adapter 统一接入、工具白名单、身份映射、权限校验、数据脱敏、签名 URL、审计日志和分阶段上线，可以让 AI Agent 真正参与招聘业务流程，同时保证系统数据安全、操作可追踪、风险可控制。
