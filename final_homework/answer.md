# 三方 AI Agent 平台接入设计方案

## 1. 接入目标

未来系统需要接入 OpenClaw、Hermes 等三方 AI Agent 平台，让外部 Agent 能以受控、安全、可审计的方式调用招聘系统能力，例如查询岗位、查询投递统计、检索候选人台账、生成招聘运营分析。

## 2. 总体思路

系统不直接暴露数据库，也不允许 Agent 绕过现有权限体系。三方 Agent 平台统一接入一个 Agent Adapter 层，由 Adapter 完成身份认证、权限映射、工具注册、参数校验、审计记录，再通过现有 Web 或 Logic 服务调用业务能力。

推荐链路：

```text
OpenClaw/Hermes
  -> Agent Adapter
  -> 鉴权与权限映射
  -> 工具调用参数校验
  -> Logic gRPC 服务
  -> MySQL / OSS / Eino
  -> 标准化结果返回 Agent 平台
```

## 3. 能力开放范围

第一阶段只开放只读能力：

1. 查询岗位列表。
2. 查询指定 HR 的岗位投递统计。
3. 查询岗位热度。
4. 查询候选人台账摘要。
5. 查询 AI 对话历史。

第二阶段在权限成熟后开放写能力：

1. 创建岗位草稿。
2. 修改岗位状态。
3. 生成候选人沟通建议。

写能力必须经过二次确认，不能由 Agent 自动无确认执行。

## 4. 身份认证与权限控制

1. 三方平台以应用身份接入，使用平台分配的 `client_id` 和 `client_secret` 换取短期访问令牌。
2. 每次工具调用必须携带租户 ID、用户 ID、角色和授权范围。
3. Adapter 将外部身份映射到系统内部 HR 或候选人账号。
4. Logic 服务继续做最终权限校验，不能只信任 Agent 平台传来的角色声明。
5. HR 只能查询本人岗位和本人岗位下的候选人投递记录。
6. 候选人不能调用 HR 管理类工具。

## 5. 工具注册设计

为 Agent 平台注册结构化工具，而不是开放任意 SQL 或任意 HTTP。

示例工具：

1. `list_jobs`：查询公开岗位。
2. `get_hr_job_stats`：查询 HR 岗位投递统计。
3. `get_applications`：查询候选人台账摘要。
4. `get_hot_jobs`：查询岗位热度。
5. `ask_recruitment_ai`：基于业务上下文发起招聘问答。

每个工具都定义输入 JSON Schema、输出 Schema、权限范围和调用频率限制。

## 6. 数据安全

1. 简历文件默认不直接返回给 Agent。
2. 如确需访问简历，只返回短有效期签名 URL，并记录访问审计。
3. Agent 输出中避免泄露身份证、联系方式等敏感信息，默认返回脱敏摘要。
4. 所有工具调用记录调用人、时间、参数摘要、结果状态和耗时。
5. 对高风险工具设置人工确认或审批流程。

## 7. 错误处理与可观测性

1. 参数错误返回明确字段错误。
2. 权限不足返回标准权限错误，不暴露内部资源是否存在。
3. 下游 Logic、MySQL、OSS、Eino 异常需要记录 trace id。
4. Adapter 为每次 Agent 调用生成 request id，贯穿日志链路。
5. 建立调用成功率、耗时、错误码和限流指标。

## 8. 实施步骤

1. 梳理可开放的业务能力清单，优先只读能力。
2. 设计 Agent Adapter 的认证、鉴权、审计和限流模块。
3. 为每个工具定义 Schema、权限范围和返回格式。
4. 将 Adapter 接入现有 Logic gRPC 服务，复用核心业务权限校验。
5. 在测试环境接入 OpenClaw 或 Hermes 沙箱。
6. 使用模拟 HR、候选人账号进行越权、注入、频控和审计测试。
7. 通过灰度方式开放给少量 HR 账号使用。
8. 根据日志和反馈逐步开放更多工具。

## 9. 风险与应对

1. 越权访问风险：Logic 层保留最终权限校验。
2. 敏感信息泄露风险：默认脱敏，简历只给短期签名 URL。
3. Agent 误操作风险：写操作必须二次确认。
4. 大模型幻觉风险：业务结论必须附带数据来源摘要。
5. 平台不可用风险：Adapter 设置超时、重试和降级提示。
