# 下一步开发计划

## 1. 当前状态

当前项目已完成最小可演示闭环：

1. `logic-grpc-service` 已实现账号、岗位、候选人档案、简历校验、投递、AI 问答和历史记录等核心业务。
2. `web-gin-service` 已实现 Gin HTTP 网关、跨域、JWT 鉴权、角色隔离，并通过 gRPC 调用 Logic 服务。
3. `hr-frontend` 已升级为 Vue 3 + Vite，实现 HR 登录注册、岗位管理（含编辑/下架/删除）、候选人台账（分页）、AI 问答（多轮上下文）页面，支持热更新。
4. `user-frontend` 已升级为 Vue 3 + Vite，实现游客岗位浏览、候选人登录注册、档案编辑、简历上传、岗位投递和投递记录页面，支持热更新。
5. 已补齐 `api.md`、`db.md`、`README.md`、`answer.md`。
6. 已完成后端测试、前端 JS 语法检查和一次端到端 HTTP 冒烟验证。

端到端冒烟验证结果：

```json
{
  "logicPortOpen": true,
  "webPortOpen": true,
  "applicationCount": 1,
  "aiAnswer": "基于 MySQL 业务数据上下文：当前你的岗位投递总人数为 1 人，岗位热度最高的是 后端工程师。"
}
```

## 2. 总体目标

下一阶段目标是把当前“内存演示版”升级为“更贴近验收要求的交付版”，重点补齐真实 MySQL 持久化、真实 OSS 签名 URL、Eino 框架调用、接口分页、前端体验和演示材料。

## 3. 优先级计划

### P0：补齐真实验收依赖

#### 3.1 MySQL 持久化

状态：已完成并通过本机 MySQL 验证。Logic 服务默认连接本机 MySQL：`root:123456@tcp(127.0.0.1:3306)/smart_recruitment?parseTime=true&charset=utf8mb4&loc=Local`，也支持通过 `MYSQL_DSN` 覆盖连接串。服务启动后会自动初始化表结构并通过 SQL 存储核心业务数据。已新增 MySQL 持久化集成测试，用于验证服务实例重建后仍可读取历史数据。

目标：将当前内存仓库替换为 MySQL 仓库，让账号、岗位、档案、简历记录、投递记录和 AI 历史在服务重启后不丢失。

建议步骤：

1. 在 `logic-grpc-service/internal/app` 下抽出仓库接口。
2. 保留当前内存仓库作为测试仓库。
3. 新增 MySQL 仓库实现。
4. 按 `db.md` 建表。
5. 通过 `MYSQL_DSN` 控制使用 MySQL 仓库。
6. 增加 MySQL 集成测试或本地手动验证脚本。

验证标准：

1. 服务重启后 HR、候选人、岗位、档案、投递和 AI 历史仍可查询。
2. `go test ./...` 通过。
3. README 增加 MySQL 初始化和连接配置说明。

#### 3.2 私有 OSS 签名上传与下载

状态：已完成腾讯云 COS 接入并通过真实上传验证。当前配置使用 `logic-grpc-service/config/config.yaml` 独立配置文件，提交 `config.example.yaml` 模板，真实 `config.yaml` 已加入 `.gitignore`。环境变量仍可临时覆盖配置文件。已新增 COS 集成测试，配置密钥后会真实上传测试 PDF 并验证返回签名 URL。

目标：用真实私有 OSS Bucket 完成简历上传和签名访问，替代当前演示签名链接。

建议步骤：

1. 新增 OSS 配置读取：`OSS_ENDPOINT`、`OSS_BUCKET`、`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`。
2. 在 Logic 服务中封装 OSS 客户端。
3. 上传时生成对象 Key，将文件写入私有 Bucket。
4. 简历记录只保存对象 Key、文件名、格式和上传时间。
5. HR 查看简历时动态生成短有效期签名 URL。
6. README 补充私有 Bucket 创建、关闭公开读和密钥配置方式。

验证标准：

1. OSS Bucket 关闭匿名访问和公开读。
2. 上传合规简历后，本地不产生源文件缓存。
3. HR 页面可通过签名 URL 下载或预览简历。
4. 非签名 URL 不能直接访问简历对象。

#### 3.3 Eino 真实调用

状态：已完成并通过 DeepSeek 真实调用验证。项目使用 Eino 的 OpenAI ChatModel 组件，配置 DeepSeek OpenAI 兼容接口 `https://api.deepseek.com` 和模型 `deepseek-v4-flash`。Logic 服务会先查询 MySQL 真实业务数据，拼接业务上下文和 HR 问题，再调用 Eino 生成回答，并将问答历史写入 MySQL。

目标：用 Eino 基础 Chat 组件替代当前规则化回答，同时继续保持“先查 MySQL，再拼业务上下文，再调用模型”的流程。

建议步骤：

1. 新增 Eino 配置读取和初始化。
2. 在 Logic 服务中新增 AI Provider 接口。
3. 保留当前本地 Provider 作为无密钥时的降级演示。
4. 新增 Eino Provider，实现基础 Chat 调用。
5. 将 MySQL 查询结果整理成标准业务上下文。
6. 将 HR 问题和业务上下文传给 Eino。
7. 将 HR 提问和 AI 回复成对写入 MySQL。

验证标准：

1. 代码中完整引用 Eino 框架依赖。
2. AI 回答前必须查询真实业务数据。
3. AI 历史刷新后能恢复。
4. 无 Eino 密钥时返回清晰配置错误或使用明确标注的本地演示 Provider。

## 4. P1：完善功能与体验

### 4.1 HR 候选人台账分页

状态：已完成。后端接口支持 `GET /api/hr/applications?page=1&pageSize=10`，Logic 与 MySQL 查询支持分页和总数，HR 前端已增加上一页/下一页与总数展示。

目标：将当前全量返回改为分页查询。

建议接口：

```http
GET /api/hr/applications?page=1&pageSize=10
```

验证标准：

1. 默认分页参数可用。
2. 返回总数、当前页、页大小和列表。
3. HR 前端支持翻页。

### 4.2 岗位编辑体验

状态：已完成。HR 前端岗位列表已增加“编辑”入口，点击后回填发布表单，支持保存修改和取消编辑；保存时调用 `PUT /api/hr/jobs/:id`，后端继续保留岗位归属校验。

目标：HR 前端支持直接编辑岗位标题和描述，而不仅是新增和下架。

验证标准：

1. HR 只能编辑本人岗位。
2. 编辑后候选人端公开岗位同步更新。
3. 越权修改仍被 Logic 服务拒绝。

### 4.3 候选人投递状态

状态：已完成。后端新增 `GET /api/candidate/applications` 返回候选人自己的投递记录；候选人前端加载岗位时同步加载已投递岗位 ID，已投递岗位按钮显示“已投递”并禁用，投递成功后立即更新页面状态。

目标：候选人端展示已投递状态，避免重复投递时只靠后端报错。

验证标准：

1. 已投递岗位按钮显示为“已投递”。
2. 刷新页面后状态仍正确。
3. 后端仍保留唯一约束和重复投递校验。

### 4.4 前端错误提示优化

状态：已完成。HR 端和候选人端已统一处理网络连接失败、后端 RPC 包装错误、登录失败、权限不足、岗位校验、档案未完善、简历格式错误、COS/AI 配置异常等提示，避免直接暴露 `Failed to fetch` 或原始 RPC 错误。

目标：让登录失败、资料未完善、简历格式错误、权限不足等错误提示更清晰。

验证标准：

1. 表单字段错误能定位到具体操作。
2. 简历格式错误提示包含允许格式。
3. 未登录、权限不足、服务不可用有不同提示。

## 6.1 已知技术说明

1. MySQL 双模式：业务服务保留内存仓库用于单元测试，启动入口默认使用 MySQL。验收演示时走 MySQL。
2. gRPC 合约：已补充标准 `.proto` 文件，并已生成 Protobuf gRPC 代码。当前 Web 服务通过 generated gRPC client 调用 Logic 服务，Logic 服务通过 generated gRPC server 注册业务实现，不再使用自定义 JSON codec。
3. 密码存储：已改为 bcrypt 哈希存储，兼容旧演示数据中的明文密码。
