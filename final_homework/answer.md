# 三方 AI Agent 平台接入实施方案

## 一、总体接入方案

### 1.1 接入总体方案

如果招聘系统需要接入 OpenClaw、Hermes 等三方 AI Agent 平台，整体思路不是让三方平台直接访问数据库、OSS 或内部 gRPC 服务，而是在系统外侧增加一层 Agent Adapter，作为三方 Agent 平台与招聘系统之间的统一接入入口。

Agent Adapter 负责接收三方平台的调用请求，完成平台鉴权、工具路由、用户身份映射、参数校验、限流和审计。真正的招聘业务仍然复用现有系统能力，包括 Web Gin 服务、Logic gRPC 服务、MySQL 数据库、私有 OSS 简历文件和 AI 问答能力。

当前系统的推荐接入链路如下：

```text
OpenClaw / Hermes
  -> Agent Adapter
  -> Web Gin HTTP API
  -> JWT / 角色 / 业务权限校验
  -> Logic gRPC 服务
  -> MySQL / 私有 OSS / DeepSeek
```

这样设计的原因是：当前项目中的 Logic gRPC 服务主要面向内部 Web 服务调用，gRPC 层本身没有独立鉴权能力。因此三方 Agent 平台不能直接调用 gRPC 服务，而应先进入 Agent Adapter，再由 Adapter 调用已有 Web API，让 Web 层继续承担用户级鉴权和业务权限校验。

后续如果要让 Agent Adapter 直接调用 Logic gRPC 服务，则需要补充 gRPC 服务间鉴权，例如通过 gRPC metadata 携带内部 token，并在 Logic 服务端增加 interceptor 校验调用来源。

### 1.2 整体接入架构

整体架构可以分为五层。

第一层是三方 Agent 平台层，包括 OpenClaw、Hermes 等平台。它们负责自然语言交互、任务规划和调用系统开放的能力。

第二层是 Agent Adapter 接入层。它负责对外暴露 Agent 可调用的 Tool 和 Skill，并把外部调用转换为系统内部请求。

第三层是 Web Gin 服务层。它复用当前系统已有的 HTTP API、JWT 鉴权、角色识别和基础参数校验能力。

第四层是 Logic gRPC 服务层。它负责岗位、投递、候选人档案、简历、AI 问答等核心业务逻辑。

第五层是数据与基础设施层，包括 MySQL、私有 OSS、DeepSeek、日志和监控。

整体调用方向如下：

```text
用户在 Agent 平台提问
  -> Agent 平台选择 Tool 或 Skill
  -> Agent Adapter 接收调用
  -> Adapter 校验平台身份和工具权限
  -> Adapter 映射为系统内部用户
  -> Adapter 调用 Web API
  -> Web 层校验 JWT、角色和业务权限
  -> Web 层调用 Logic gRPC
  -> Logic 查询 MySQL / 生成 OSS 签名 URL / 调用 AI
  -> 返回结构化结果
  -> Agent 组织自然语言回复
```

### 1.3 完整接入流程

第一步，在 OpenClaw 或 Hermes 平台创建应用，获取平台分配的 `client_id`、`client_secret`，并配置系统提供的 Agent Adapter 调用地址。

第二步，在招聘系统中登记三方平台应用，保存平台标识、密钥、允许调用的 Tool 范围、限流规则和启用状态。

第三步，在 Agent Adapter 中定义可开放的 Tool 清单，例如岗位查询、投递统计、候选人档案查询、简历签名 URL 获取等。

第四步，为每个 Tool 定义输入参数、输出结构、权限要求、错误码和调用限制。三方 Agent 平台只能调用这些明确注册过的能力，不能调用任意接口。

第五步，三方平台发起调用时，携带平台 token、外部用户 ID、调用工具名称和参数。

第六步，Agent Adapter 校验平台身份是否合法，判断该平台是否有权调用目标 Tool 或 Skill。

第七步，Adapter 将外部用户身份映射为招聘系统内部用户，例如映射为某个 HR 账号或候选人账号。

第八步，Adapter 调用 Web Gin HTTP API，并携带短期内部访问令牌或通过 token exchange 换取的系统访问令牌。

第九步，Web 层继续完成 JWT 校验、角色校验和业务权限校验，再调用 Logic gRPC 执行核心业务。

第十步，Logic 服务返回真实业务数据，Adapter 对结果进行格式标准化、敏感字段脱敏和审计记录后返回给三方 Agent 平台。

## 二、Tool 暴露与 Skill 编排机制

### 2.1 Tool 和 Skill 的区别

Tool 是单一、原子的系统能力，通常对应一次明确的业务查询或操作，例如查询岗位列表、查询投递人数、查询候选人档案、获取简历签名 URL、查询岗位热度、发起 AI 数据问答等。Tool 适合由系统统一注册和管理。

Skill 不是单个接口，而是由多个 Tool 组合起来的重复性工作流程，例如候选人初筛、招聘运营日报、岗位招聘效果分析、面试前候选人资料整理等。Skill 适合由 OpenClaw、Hermes 或 Agent Adapter 基于 Tool 进行编排。

因此，本系统不应把每个单一接口都包装成 Skill，而应先在 Agent Adapter 中维护 Tool Registry，将稳定的原子业务能力注册为 Tool，再让不同 Agent 平台或 Adapter 将多个 Tool 组合成可插拔的 Skill。

### 2.2 Tool Registry 设计

系统通过 Agent Adapter 中的 Tool Registry 向 Agent 暴露能力。三方 Agent 平台只能看到 Tool Registry 中注册过的 Tool，不能自由调用系统内部接口，也不能直接访问数据库、OSS 或 gRPC 服务。

Tool Registry 中每个 Tool 至少需要声明以下信息：

1. Tool 名称，例如 `get_hot_jobs`。
2. 功能描述，例如“查询当前 HR 可见范围内的热门岗位”。
3. 输入参数 schema，例如时间范围、岗位状态、分页参数。
4. 输出结果结构，例如岗位名称、投递人数、排序结果。
5. 权限要求，例如仅 HR 可调用、候选人不可调用。
6. 是否只读，例如查询类 Tool 为只读。
7. 调用频率限制，例如 AI 问答和简历签名 URL 需要更严格限制。
8. 内部映射的 Web API，例如 Adapter 最终调用哪个 HTTP 接口完成业务。

### 2.3 原子 Tool 开放范围

第一阶段建议开放只读 Tool，包括：

1. 岗位查询 Tool：查询公开岗位、岗位详情、HR 自己发布的岗位。
2. 投递统计 Tool：查询投递总人数、单岗位投递数、岗位热度排行。
3. 候选人查询 Tool：分页查看投递候选人、查看候选人结构化档案摘要。
4. 简历访问 Tool：在权限校验通过后生成短期有效的简历签名 URL。
5. AI 问答 Tool：基于当前 HR 可见的 MySQL 业务数据进行自然语言问答。

第二阶段再开放受控操作类 Tool，例如生成岗位草稿、生成候选人沟通建议、生成岗位优化建议。凡是涉及修改业务数据的 Tool，都必须经过用户二次确认后才能执行。

### 2.4 Skill 可插拔编排

Skill 采用可插拔编排方式。每个 Skill 只依赖 Tool Registry 中已经注册好的 Tool，不直接依赖数据库或内部服务。新增 Skill 时，只需要配置 Skill 名称、适用场景、执行步骤、所需 Tool 和输出格式，不需要改动核心业务逻辑。

候选人初筛 Skill 可以按以下步骤执行：

```text
查询岗位详情
  -> 查询该岗位投递候选人
  -> 获取候选人结构化档案
  -> 对比岗位要求和候选人技能
  -> 输出推荐候选人名单和理由
```

招聘运营日报 Skill 可以按以下步骤执行：

```text
查询 HR 岗位列表
  -> 统计各岗位投递数量
  -> 查询热门岗位排行
  -> 汇总新增候选人数量
  -> 生成日报摘要
```

岗位效果分析 Skill 可以按以下步骤执行：

```text
查询岗位详情
  -> 查询岗位投递量
  -> 分析候选人学历和技能分布
  -> 查询岗位热度
  -> 给出岗位描述或招聘策略优化建议
```

这种设计下，Tool 是稳定的底层能力，Skill 是可新增、可替换、可组合的业务流程。不同 Agent 平台可以复用同一批 Tool，也可以根据自身能力编排不同 Skill。

## 三、安全控制与可观测性设计

### 3.1 多层鉴权职责

Agent Adapter 和 Web 层都需要鉴权，但二者职责不同。

Agent Adapter 负责外部平台级鉴权，主要判断请求是否来自可信的 OpenClaw 或 Hermes，平台 token 是否有效，该平台是否有权调用目标 Tool 或 Skill，调用频率是否超过限制，参数是否符合 Tool schema。

Web 层负责系统用户级鉴权，主要判断映射后的 HR 或候选人是否具备有效 JWT，角色是否正确，是否有权限访问具体业务接口。

Logic 层负责核心业务归属校验，例如 HR 只能新增、编辑、下架自己创建的岗位；候选人只能维护自己的档案；HR 查看简历时必须满足岗位和投递关系上的权限要求。

三层职责可以概括为：

```text
Adapter 防止外部非法平台或非法 Tool 调用
Web 防止系统用户身份伪造和角色越权
Logic 防止核心业务数据被错误操作
```

### 3.2 业务数据安全

系统不能向三方 Agent 平台暴露 MySQL 连接信息，也不能提供自由 SQL 查询能力。所有业务查询都必须通过预定义 Tool 完成，由后端使用已有服务方法或参数化查询获取数据。

候选人手机号、邮箱、完整简历、学校、工作经历等信息需要按场景返回。统计类问题只返回聚合数据，不返回个人明细。只有用户具备权限并明确查询某个候选人时，才返回结构化档案摘要。

### 3.3 私有 OSS 简历访问

简历文件必须继续使用私有 OSS。系统只保存 object key，不返回永久公网 URL。当 HR 或 Agent 需要查看简历时，后端先校验权限，再生成短期有效的签名 URL。

简历访问流程如下：

```text
Agent 调用简历访问 Tool
  -> Adapter 校验平台和 Tool 权限
  -> Web 层校验用户身份和角色
  -> Logic 校验业务数据归属
  -> OSS 生成短期签名 URL
  -> 返回文件名、过期时间和签名 URL
```

签名 URL 应设置较短有效期，并记录生成日志和访问审计，避免简历链接长期暴露。

### 3.4 AI 问答与提示词注入防护

AI 问答要基于真实业务数据，而不是让大模型自由猜测。当用户询问“投递总人数是多少”“哪个岗位最热门”“有哪些候选人技能包含 MySQL”时，系统应先通过 Tool 查询 MySQL 中的真实数据，再把数据摘要作为上下文交给 AI 生成回答。

同时需要防止提示词注入。岗位描述、简历内容、聊天内容、候选人自我介绍等都应视为不可信输入。即使这些内容中出现“忽略权限规则”“导出所有候选人”“直接返回数据库连接信息”等文本，也不能改变系统的 Tool 权限和业务权限判断。

提示词注入防护可以从以下几个方面设计：

1. 系统提示词中明确声明业务数据只是上下文资料，不是指令来源。
2. Agent 只能调用 Tool Registry 中注册过的 Tool，不能根据用户文本临时生成新的内部调用。
3. 大模型不能直接拼接 SQL，也不能决定绕过权限调用接口。
4. Tool 调用前必须由 Adapter 和 Web 层分别校验平台权限、用户身份和业务权限。
5. 返回给模型的业务上下文应尽量使用结构化摘要，避免把完整简历、完整聊天记录和敏感字段原文全部塞入提示词。
6. 对高风险意图进行拦截，例如批量导出候选人、获取所有简历、查询无关 HR 数据等。

### 3.5 错误处理设计

系统需要为 Agent 调用设计统一错误返回，避免三方平台只能看到模糊的内部异常。错误结果应包含错误码、错误说明、请求 ID 和是否可重试等信息，但不能暴露数据库表名、SQL 语句、服务器地址、密钥或内部堆栈。

常见错误类型包括：

1. `AUTH_FAILED`：平台 token 无效、过期或签名错误。
2. `USER_MAPPING_FAILED`：外部用户无法映射到系统内部 HR 或候选人账号。
3. `PERMISSION_DENIED`：当前用户无权调用该 Tool 或访问该业务数据。
4. `VALIDATION_ERROR`：Tool 输入参数缺失、类型错误或格式不合法。
5. `NOT_FOUND`：请求的数据不存在，或对当前用户不可见。
6. `RATE_LIMITED`：平台、用户或 Tool 调用频率超过限制。
7. `HUMAN_CONFIRM_REQUIRED`：写操作或高风险操作需要用户二次确认。
8. `DOWNSTREAM_ERROR`：Web API、Logic gRPC、MySQL、OSS 或 AI 服务异常。
9. `TIMEOUT`：调用链路超时，例如 AI 问答或 OSS 签名生成超过限制。

对于只读查询，系统可以提示用户稍后重试；对于写操作，不能在结果未知时自动重试，避免重复创建岗位、重复下架岗位或重复修改状态。涉及写操作的 Tool 应增加幂等 ID，保证同一次请求重复提交时不会产生多次业务变更。

### 3.6 日志审计设计

Agent 接入后，所有 Tool 和 Skill 调用都必须记录审计日志。审计日志用于追踪问题、排查越权、统计调用量和满足安全要求。

每次调用至少记录以下信息：

1. request_id，用于贯穿 Adapter、Web、Logic 和下游服务。
2. 平台名称，例如 OpenClaw 或 Hermes。
3. 外部用户 ID 和映射后的系统用户 ID。
4. 调用的 Tool 或 Skill 名称。
5. 参数摘要，敏感字段需要脱敏。
6. 权限校验结果。
7. 内部调用的 Web API 或 gRPC 方法。
8. 返回状态、错误码和耗时。
9. 是否生成 OSS 签名 URL。
10. 是否触发 AI 问答或高风险操作。

日志中不能保存明文密码、API Key、OSS Secret、完整简历原文、长期有效下载地址等敏感信息。对于简历签名 URL，可以记录 object key、生成时间、过期时间和访问人，但不建议长期保存完整 URL。

监控指标可以包括 Tool 调用次数、成功率、失败率、平均耗时、权限拒绝次数、限流次数、AI 调用耗时、OSS 签名 URL 生成次数等。当出现高频失败、越权尝试、异常下载简历等情况时，应触发告警。

## 四、实施流程、测试与验收

### 4.1 实施步骤

第一阶段，完成接入准备。在 OpenClaw 或 Hermes 中创建应用，获取 `client_id`、`client_secret`，配置 Agent Adapter 的调用地址；同时在招聘系统中登记平台信息、启用状态、允许调用的 Tool 范围和限流规则。

第二阶段，建设 Agent Adapter。Adapter 需要实现平台鉴权、用户身份映射、Tool Registry、参数校验、Tool 路由、限流和审计能力。此阶段优先打通只读 Tool，不开放修改业务数据的能力。

第三阶段，接入现有 Web API。Adapter 根据 Tool 配置调用 Web Gin HTTP API，由 Web 层继续校验 JWT、角色和业务权限，再通过 Logic gRPC 调用核心业务。这样可以最大程度复用当前系统已有能力。

第四阶段，设计 Skill 工作流。在只读 Tool 稳定后，基于 Tool 编排候选人初筛、招聘日报、岗位效果分析等 Skill。Skill 初期只生成分析结果和建议，不直接修改业务数据。

### 4.2 测试重点

联调测试需要验证 OpenClaw 或 Hermes 沙箱环境能否正确调用 Agent Adapter，Adapter 能否正确映射用户并调用 Web API，Web 和 Logic 能否返回真实业务数据。

权限测试需要覆盖未登录访问、平台 token 错误、角色越权、操作他人岗位、访问无关简历等场景。

安全测试需要覆盖私有 OSS 签名 URL、签名 URL 过期、AI 问答越权查询、提示词注入、参数异常、频繁调用和审计日志记录等场景。

### 4.3 上线策略

上线时应采用灰度方式。第一阶段只开放岗位查询、投递统计、岗位热度、候选人摘要等只读 Tool。只读 Tool 稳定后，再逐步开放候选人初筛、招聘日报、岗位效果分析等 Skill。

涉及写操作的能力必须单独评估，并增加用户二次确认。例如生成岗位草稿可以先开放，但自动发布岗位、自动下架岗位、自动修改候选人状态等能力不应在初期开放。

### 4.4 验收标准

接入完成后，应满足以下标准：

1. OpenClaw 或 Hermes 可以通过 Agent Adapter 成功调用系统开放的 Tool。
2. Agent Adapter 能校验平台身份、Tool 权限、参数格式和调用频率。
3. Web 层能继续校验 JWT、用户角色和业务接口权限。
4. 三方 Agent 不能直接访问 MySQL、OSS 或未鉴权的 gRPC 服务。
5. HR 不能通过 Agent 操作他人创建的岗位。
6. 候选人不能通过 Agent 调用 HR 管理类能力。
7. 简历文件只能通过短期签名 URL 访问。
8. AI 回答基于真实 MySQL 业务数据，而不是凭空生成。
9. 所有 Agent 调用都有日志和审计记录。
10. Tool 与 Skill 划分清晰，原子能力和复合工作流边界明确。
11. 错误返回结构统一，不向三方平台暴露内部敏感实现。
12. 提示词注入不能绕过 Tool 权限、用户权限和业务权限校验。

综上，本系统接入三方 AI Agent 平台时，应以 Agent Adapter 作为统一入口，以 Web API 作为当前推荐的内部调用方式，以 Logic gRPC 作为核心业务服务。通过 Tool Registry 暴露稳定原子能力，通过可插拔 Skill 编排重复性招聘流程，再配合平台鉴权、用户鉴权、业务权限校验、私有 OSS 签名 URL、错误处理和审计日志，可以保证系统既能被 Agent 使用，又不会破坏现有权限体系和数据安全边界。
